# @xochi/client

Cross-chain swap client for the Xochi Worker API (`https://api.xochi.fi/api/*`): a transport, a pure trade state machine (`update(model, msg) -> [model, effects]`, `view(model)`), the fund-safety checks it runs on every quote, and the layered fee reference.

## Install

```bash
npm install @xochi/client
```

Node 22+ or a current browser. ESM + CommonJS with types.

## Transport

```ts
import { createXochiClient } from "@xochi/client";

const xochi = createXochiClient({
  baseUrl: "https://api.xochi.fi",
  getAuthToken: () => session.token, // optional
  onAuthExpired: (e) => session.reauthenticate(e),
});

const quote = await xochi.getQuote(request);
```

- `execute` makes one attempt. Never re-post a failed one: poll `getIntentStatus` until the intent ends, since even a refused execute leaves its signed request executable until it expires. The one exception is `ApiError.notAccepted`, below. Whether a failed answer can still have moved funds is `ApiError.inDoubt`, below; the machine polls every failed execute either way.
- `getIntentStatus` returns the status, `{ notFound: true }` on 404, or `null` on a transient failure.
- An `execute` response may carry `readToken`, served once (xochi#563) and kept only for the intent the execute named (one served under another `intent_id` is dropped). Keep it with the intent and pass `{ readToken }` to `getIntent` / `getIntentStatus`, which send it as `X-Xochi-Read-Token`; without it a stealth intent's on-chain legs (tx hashes, chain ids, `sending` / `receiving`) are omitted. For a shielded intent the token never unlocks the Aztec identifiers (note hash or commitment, nullifier, tx hash, block) or any timestamp or amount (leg timestamps, `createdAt`, `updatedAt`, `fromAmount`, `toAmount`): shielded is not offered, and once it is SPEC.md §5.1 serves them only to an owner-authenticated request. A failed execute may carry it too (a 502 when funds may have moved, or a 2xx whose other fields fail validation): take it once with `takeApiErrorReadToken(error)`, before the error reaches any reporter. It is never a property of the error. It is a bearer secret: never log it or put it in a URL.
- To keep the full view across a reload, persist the token next to the intent id as you would a session credential (same-origin storage, never a URL, a log or a message the machine replays; `ResumeRequested` carries none), and delete it once the intent is no longer shown. Not persisting it is safe: after a reload the intent reads status-only.
- The token is read-only: the transport sends it only on these two reads. It never authorizes a hold, an acknowledgement, a claim or any other write, and holding it is not an authenticated recipient channel: it is a bearer secret the host holds, not proof of the recipient.
- The token can be lost for good: an execute that times out or aborts, a reset connection, or a 5xx whose body is not JSON (or is cut by the 8 KiB read below before its `read_token` closes) leaves no token to take, and the server never re-issues one. Wallet SIWE for the intent's wallet is then the only way back to the full view.
- Every intent read (`getIntent`, `getIntentStatus`, `getIntentHistory`) and `execute` are pinned to the `baseUrl` origin: no other host's answer becomes an intent's status, record or execute result. A refusal is a `RedirectRefused`: `getIntent` / `getIntentHistory` / `execute` reject with it, and `getIntentStatus` reports it once per intent through `log` and returns `null` (a transient failure: the poll runs on).
  - A read carrying the token is sent with `redirect: "manual"` (not `"error"`, which Cloudflare Workers rejects), since fetch forwards a custom header across origins and following would hand the token to whatever host the `Location` names. On Node (undici) and Workers, one plain redirect (301/302/303/307/308) whose `Location` is on the origin is followed by hand, once, with the token (a path migration). Every other redirect is refused: a further 3xx, a `redirected` response, a `response.url` off the origin or naming no url at all, or an `opaqueredirect`. A browser answers every manual redirect with an `opaqueredirect` (no status, no `Location`), so in a browser a redirected token read is always refused.
  - A read without the token follows redirects natively and is accepted only if its final `response.url` is on the origin (a `redirected` response that names no `url` is refused). `getIntentStatus` reads again this way when its token read is refused, so behind a same-origin redirect a browser still gets the status-only view.
  - `execute` is sent with `redirect: "manual"` and follows nothing: a 3xx, an `opaqueredirect`, a `redirected` response, or a `response.url` off the origin or naming no url at all is refused unread (no result and no token taken from it), so a redirect never re-posts the signed request. That refusal is in doubt, like any failed `execute` that is not an `ApiError`: the machine shows "Still confirming" and polls. So a redirect in front of `execute` (http to https, a www/apex rule, an access proxy) means the execute never reaches the Worker: the swap reads "Still confirming" until the Worker, read past the intent's signed deadline plus `QUOTED_EXPIRY_GRACE_SECS` (60 s), finishes the never-claimed intent `failed` with `not_executed`, which offers Retry; the machine polls at least that long ([Fund safety](#fund-safety)). Point `baseUrl` at the origin that answers `/api/intent/execute` itself.
- An injected `fetch` MUST honour `redirect: "manual"` and return the response it fetched. One that follows redirects has sent the token to the `Location` host before any check runs. A response that names no `url` (one the injected fetch built, such as `new Response(body, init)`, which may stand for a redirect it followed) is refused on `execute` and on a token read, so behind such a wrapper every execute is refused and its read token lost; a read without the token cannot tell and accepts it. The transport says so once, at `error` through `log`, on the first answer naming no url (normally the first quote, before any execute), and the refusal's message names it.
- `getIntent` rejects a `readToken` not of the issued shape before any request. `getIntentStatus` instead reads anonymously and reports it once per intent through `log`, so a caller bug never stalls the poll.
- An error body (any non-ok response) is read up to its first 8 KiB and no further: reading stops once the cap is full (a body that fills it counts as cut), and the rest is cancelled unread. Everything below works on that prefix. A cut JSON body does not parse, so `takeApiErrorReadToken` reads its token from the prefix by strict match: only from a prefix that opens a JSON object with exactly one `"intent_id"`, equal to the executed intent, and exactly one `"read_token"` whose value is a whole token, both keys of that object itself (not of a value nested in it). A body that does not arrive within the attempt's timeout fails the attempt as a timeout, its status and `Retry-After` lost with it.
- `ApiError.message` carries a capped, redacted excerpt of the error body, never the raw body; its log line (`Request failed after retries`) carries the same excerpt. In order:
  1. `\u{…}`, `\uXXXX`, `\xXX`, JSON's `\n`, `\r`, `\t`, `\b`, `\f` and `\/`, `%XX` (as UTF-8) and numeric `&#…;` escapes (any number of leading zeros, `;` optional) are decoded, every non-ASCII character but a space is folded to its compatibility form (NFKD: fullwidth `Ａ１` reads `A1`), then invisible characters (format and default-ignorable characters, controls other than tab and line breaks) and complete markup tags (`<p>`, `</b>`, `<a …>`, `<!…>`, `<?…>`; a bare `<` is text) are removed; this repeats for nesting up to three deep, and a body still changing after that is shown as `[redacted]` alone. Backslashes as text stay as written: backslash escapes are read left to right with JSON's `\\` as a pair, so no escape starts at the backslash a pair ends (`C:\\keys\\nAbc`, `C:\\u0041` and `C:\\x41` keep their `n`, `u0041` and `x41`), and nothing decodes to a backslash (`\u005c`, `\x5c`, `%5C`, `&#92;` and a fullwidth `＼` stay as written), so no decoded backslash escapes the character after it.
  2. The result is cut to its first 2048 characters. After a cut, here or by the 8 KiB read, an unclosed tag at the end and the base64url run or unfinished escape the cut ends in are dropped, and `…` appended.
  3. Possible tokens are collected from the whole prefix: the body's own `read_token`, the value after any read-token key (`read_token`, `readToken`, `X-Xochi-Read-Token`, any case, quoted or escaped), and, both decoded and as written (decoding a raw `\n` eats the first character of a token written after a backslash, whole or split), every base64url run of at least 43 characters that is not hex and every token split into pieces: combining marks and non-ASCII spaces or line separators between base64url characters are ignored, and pieces of 8 or more characters that are not hex and hold a digit, `-`, `_` or mixed case are joined across one space, tab, `.`, `,`, `;`, `|`, `/` or line break (LF, CRLF or a lone CR; after a line break that follows a piece of 16 or more that is not a name, the last piece may be any run) when they make at least 43 characters. A piece that reads as a CamelCase or `snake_case` name (`PermitWitnessTransferFrom`, `pull_failed`) joins only when the unbroken sequence of linked pieces it sits in holds one that does not: a list of names stays readable, and random pieces that happen to read as names, one or several in a row, do not break the chain they sit in.
  4. Every 16-character fragment of a possible token, in base64url, standard base64, or hex of its bytes or of its characters (any case), is replaced wherever it appears, matched with every character outside that alphabet ignored (`0x` prefixes too), so separators inside an echo hide nothing; the span it covers, separators included, is replaced.
  5. The value after any read-token key, and every base64url run of at least 43 characters that is not hex, are replaced.

  Tx hashes and `0x` addresses stay readable; any other long base64url value (a base58 address, an opaque id, two ids one space apart) is redacted too, with its fragments.

  Not covered: an echo of a token no read-token key in the prefix names, and that is not a base64url run or a joinable split of one (its hex, its standard base64, its raw bytes as `\xNN`, a split piece under 8 characters or reading as a word, pieces that all read as names with no other piece in their chain, or pieces split by any other separator or by more than one character, such as `, `, `:` or a nested JSON string's `\\n`); and a piece of under 16 characters with other base64url text on both sides, or left at a cut. A 16-character window is 96 random bits, so what stays readable of a token is a piece shorter than that.

- A read without the token (or an owner SIWE session) is the server's status-only view. `getIntentStatus` then carries `legsWithheld: true` and `settlementConfirmed` (the machine shows a confirmed fill as delivered, `substatus: "filled"`, without changing `status` or `terminal`, and sets `IntentState.legsWithheld` until an owner read clears it; when the flag counts is `withheldSettlementConfirmed`'s rule); `getIntent` returns a `WithheldIntentRecord` (`legsWithheld: true`, its status decoded like a status poll's, no tokens, amounts, fees or timestamps) rather than an `IntentRecord`. Recovery: the token, else wallet SIWE (above).
- 429/503 raise `ApiError` with `retryAfter` (absolute unix seconds, capped at 600 s, `MAX_RETRY_WAIT_SEC`), read from the `Retry-After` header (delta), else `X-RateLimit-Reset` (absolute), else a JSON body's camelCase `retryAfter` (absolute). The not-accepted answer below is the one exception.
- `ApiError.notAccepted` is `true` only on the Worker's not-accepted answer to `execute`: a 503 whose body is a JSON object with `success` the boolean `false`, `status` `"quoted"`, `accepted` the boolean `false`, `intent_id` equal to the executed intent, and `retry_after` a positive finite number (delta seconds), and that is not in doubt (`ApiError.inDoubt`, below; the two are never both `true`). The Worker sends it only after undoing its own claim, on a solver refusal that provably ran before the intent was claimed or any pull sent, so the intent is `quoted` again and the same request may be sent again. Anything else is `false` and is never resent, classified exactly as without the marker: another status (429, 500, 502, 409, ...), a missing, string or non-boolean marker, any other `success` or `status` (the Worker's lost-race answer `status: "executing", reconciling: true` included), another intent's id, a missing, zero, negative or non-numeric `retry_after`, a body that is not a JSON object or is cut by the 8 KiB read. Its `retryAfter` is the wait the body's `retry_after` names (the Worker's choice, jitter included), counted from when the answer is read and rounded up to the next whole second so it never ends early; a readable numeric `Retry-After` header moves it only later, never earlier; `X-RateLimit-Reset` and a body `retryAfter` are not read for it; capped at 600 s. Pass the flag into the machine as `ErrorReport.notAccepted` and let the machine resend; `execute` itself never retries.
- `ApiError.inDoubt` is `true` on a failed `execute` whose answer cannot vouch that nothing moved for the executed intent. It is `false` only on the three Worker answers that speak for the intent, not just for this request: the not-accepted 503 above (it undid its own claim, and the intent is `quoted` again); its 502 with `success: false`, `status: "failed"` and `substatus: "not_executed"` for the executed intent (it ended the intent with nothing moved; the marker's sources: `NOT_EXECUTED_SUBSTATUS`); and its 409 with `error_category: "promo_unavailable"` (the promo redemption is keyed by intent and idempotent, and every claim follows one, so a refused redemption means no request has claimed the intent). Every other answer refuses this request only, while another request for the same intent (another tab, a replayed request) may hold its claim, so it is in doubt: every 400, 401, 403, 404 and 422, from the Worker or from anything in front of it (the Worker answers its parse 400 and its 403 `api_key_intent_mismatch` before it reads the intent's status, and its other 400s and 401s, the signed-deadline 400 included, from a row it read before, which another request can claim in between; an edge never reads the intent); the 400 for an intent no longer `quoted` and any other 409 (another request holds or held the intent); every 429 (the Worker's plain 429 also answers an intent another request holds; its resendable rate limit is the not-accepted 503); any other 5xx, JSON or not (the Worker's catch-all 500 can follow its call to the solver); and an unmarked 502 `failed` (a solver failure nothing vouches for). No error text is read, so a reworded Worker message can only leave an answer in doubt. Any body carrying a `read_token` or `reconciling: true` is in doubt, whatever its status. A failed `execute` that is not an `ApiError` (a timeout or abort, a reset connection, a `RedirectRefused`, `Invalid response format`) is in doubt too. `false` says nothing had moved when the Worker answered, not that the order is over: unless the answer is the marked 502, the intent is still `quoted` and its signed request executable until it expires. Word an input error (a bad signature, an expired quote) from `code` and the message, not from this flag, which is for the host's own copy and logs; the machine does not take it, since it polls every thrown execute and only the poll's `failed` with `not_executed` (or, while "not sent yet", a 404) offers Retry ([Fund safety](#fund-safety)).
- Quote and execute bodies are validated against `QuoteResponseSchema` / `ExecuteResponseSchema` (undeclared top-level keys tolerated). The one exception is a malformed `read_token`, dropped (`readToken` undefined) rather than failing the execute (why: `ExecuteResponseSchema`). Each attempt's timeout stays armed until the body is read and cancels the body when it fires. The only quote-cache TTL is `DEFAULT_TIMEOUTS.quoteCacheTtlMs` (15 s).
- The exported `QuoteResponseSchema` / `ExecuteResponseSchema` are `.strict()` (the declared wire shape); the transport validates with a `.passthrough()` copy so undeclared served fields (e.g. `escrow`) reach the signer checks. A consumer running the exported schema directly is stricter than the transport.

## State machine

```ts
import { init, update, view, type MsgBody } from "@xochi/client";

let model = init(
  {
    solverPin: { erc3009Allowlist: [...], permit2Allowlist: [...], requirePin: true },
    pullRecipients: { 8453: { erc3009: "0x...", permit2: "0x..." } }, // your pin
    depositAttestationSigner: "0x...", // your pin; null refuses every deposit route
  },
  context,
);

function dispatch(body: MsgBody) {
  const [next, effects] = update(model, { ...body, now: Date.now(), hidden: false });
  model = next;
  for (const effect of effects) perform(effect); // Api / Wallet / Timer / Emit
  render(view(next));
}
```

Lifecycle rules the machine enforces, beyond the signer checks under [Fund safety](#fund-safety):

- A quote whose `preview` disagrees with the request is refused; any quote carrying `eip712` is checked whether or not it claims to be a preview.
- Confirm is gated on `canSignQuote` and `holdsCurrentQuote`: a held quote is signable (and a deposit address revealable) only while its quoted amount and trade match the form. The trade key is built from the same normalised fields as the quote request (`normalizeTradeFields`), so an edit that leaves the request unchanged keeps the quote.
- A new amount, a trade/wallet context change, Reset, a resume, or entering `signing` / `awaiting_deposit` / `executing` drops in-flight quote flights. Refresh is ignored past `quoting`, Allocate outside `ALLOCATABLE_STATES` (idle / pending / quoting / quoted), and a quote reply that finds the trade past `quoting` or ended is dropped; a failed allocation never reopens a trade as `quoted`.
- The sign ceremony survives `signing -> executing` only for the machine's own execute step (`sign.stage === "execute"`); a status-driven move abandons it, and a signature reply outside `signing` is ignored.
- `StreamStatus` frames for another intent are ignored. Read stream frames with `mapStatusFrame`: it passes in-flight frames only, so every terminal arrives by the poll with its receipt and reason. A `failed` frame a host dispatches itself follows the poll's rule ([Fund safety](#fund-safety)).
- An execute reported `notAccepted` (below) waits with no status read and resends from the `execute` timer under a new flow id; a status move off `executing`, Reset, or any end of the ceremony drops the pending resend (`clear:execute`). **Hosts must schedule the `execute` timer** like the others and render the `busy` signing slot. A host that drops the timer is slowed, not stranded: the poll timer stays armed through the wait, and the first poll tick (every `STATUS_POLL_MS`, 4 s) or returning tab (`VisibilityChanged`) at or after the resend time does the timer's work, so the resend goes up to 4 s late. The deadline check still decides: a resend that late can fall inside `EXECUTE_RESEND_MARGIN_SECS`, and then the machine stops resending ("not sent yet", [Fund safety](#fund-safety)) instead.

## Fund safety

The machine checks every quote against the request (via `@xochi/signer`), the pull against your pins, the payout against what was rendered, and deposit attestations against your signer; claims are checked before signing. All fail closed: a failing quote is never signable, a failing deposit address never shown.

- **Pins are yours.** Never derive `pullRecipients` or `depositAttestationSigner` from `/api/capabilities` (same channel as the quote).
- **Quotes with an `escrow` envelope are refused.**
- **A deposit address is never revealed with under 60 s of its attested window left.**
- **On resume, run stored deposits through `verifyStoredDeposit`** and render and re-persist `result.stored`, not your input.
- **The machine never sees a read token, and judges every execute reply itself.** `ExecuteReplied` carries the response without the token (`ExecuteReply`): `const { readToken, ...response } = await xochi.execute(request)`, retain `readToken` outside replayable state keyed by the intent id, and dispatch `{ ok: true, response }` (or a token-free `ErrorReport`); pass the retained token to `getIntentStatus` when performing a `status` effect. A thrown execute (whatever `ApiError.inDoubt` says), a reply it cannot read as an execute response for this intent (intent ids compare exactly), a status it does not model, and any reply with reconciling on (`reconciling` is the server's flag when it sends one, else on whenever success was withheld) leave the intent in flight, shown in doubt ("Still confirming"), and polled until it ends or the poll's ceiling stops it (`IntentState.pollExhausted`): `STATUS_POLL_FLAT_CEILING_ATTEMPTS` (150) intervals of 4 s with no status change, a read the intent cannot move to (`quoted` after an execute) included; in `executing` at least until the Worker's finish of an intent no execute claimed (`unexecutedFinishAt`: the later of the quote's `expiry` and the signed intent's `deadline`, plus `QUOTED_EXPIRY_GRACE_SECS`, 60 s) and one more poll, in `awaiting_deposit` until 10 minutes past the deposit deadline; never past 2 hours. An execute that never reached the Worker (a refused redirect, a timeout before any answer) reads `quoted` until that finish, then `failed` with `not_executed`: Retry.
- **After an execute, only the Worker's `not_executed` offers Retry.** A `failed` read after an execute or a revealed deposit address (any in-flight status: `executing`, `bridging`, `settling`, `awaiting_deposit`, where a deposit may have been sent unseen), from the poll, a `StreamStatus` frame or a final execute reply (`failed` with `success: false` and `reconciling` off), is the Retry view (phase `failed`) only when it carries `substatus: "not_executed"`: the Worker's mark on a `failed` where nothing moved (every source it has: `NOT_EXECUTED_SUBSTATUS`; xochi#686). Every other `failed`, bare or granular (`fill_failed`, `pull_failed`, `refund_failed`, ...), in doubt or not, ends at once in the terminal "may have moved" view: `IntentState.mayHaveMoved`, phase `may-have-moved`, the poll stopped, no Retry, and no quote, wallet reset, Refresh or cleared amount leaves it until Reset, which starts a new trade. Suggested copy, which promises no refund (a `refund_failed` ends here too): "This order did not complete. Funds may have moved. Check Activity before trading again." Against a Worker that does not send the marker (before xochi#686), every `failed` after an execute ends there. On a reload, read the record with `getIntent` and pass its `substatus` (`IntentRecord.substatus`) as `ResumeRequested.substatus`, never a stored copy: a resumed `failed` is Retry only with the marker, and the machine trusts it as it trusts every reply the host relays. A failure before any execute or revealed address (a wallet or quote failure) is the Retry view as before; the machine's own not-accepted give-up is not (below).
- **Only an explicit not-accepted refusal is retried, and only the same signed request.** Build the thrown execute's `ErrorReport` with `notAccepted: error instanceof ApiError && error.notAccepted` and `value` the usual `StructuredError` (`code`, `retryAfter`); never set it from anything else. It is the only flag the machine reads from a thrown execute. `value.retryAfter` is the `ApiError`'s absolute `retryAfter`, never the body's delta `retry_after`: one more than a minute before `now` is no target (`stale_retry_after`), and the machine stops resending rather than resend at once. Exactly `true` makes the failure not in doubt (no reconciling): the receipt's signing slot reads `{ kind: "busy", retryAt, resend, of }` (phase `submitting`; suggested copy, which makes no funds claim since the signed request stays executable during the wait: "Solver busy. Resending in Ns (retry r of n)." and "Keep this tab open. If it closes, this tab will not resend the order."), and when the wait ends ([State machine](#state-machine)) the machine dispatches the identical `ExecuteRequest` (same signatures, same nonce). At most `MAX_EXECUTE_RESENDS` (3) resends, each only with a `retryAfter` and only if it lands at least `EXECUTE_RESEND_MARGIN_SECS` (5 s) before the earliest of the quote's `expiry`, the signed intent's `deadline` and the pull authorization's `validBefore` / `deadline` (`decideExecuteResend`, `executeDeadline`). Otherwise (a 4th refusal, which need not be the Worker's budget: its wallet rate limit counts none; no or a stale `retryAfter`; a resend past the deadline) the machine stops resending and shows "not sent yet": `IntentState.notSent`, phase `not-sent`, the refusal as its error, no Retry, since the Worker un-claimed the intent and its signed request stays executable until it expires. The Worker's execute answer `200 { success: false, status: "quoted", reconciling: true }` (it ended its own claim but could not finish the intent) is "not sent yet" the same way. Either is read in doubt instead, polled like any thrown execute, when the intent already reads in doubt (reconciling). The poll runs on (no "Still confirming" escalation) until the Worker ends the intent. Usually its quote sweep does, first: nearly every give-up follows an un-claim, and an intent the Worker claimed and un-claimed is finished `failed` with `not_executed` by the sweep's first run (every 5 minutes) past the quote's creation plus 90 s (its 30 s TTL plus 60 s), so 90 s to about 6.5 min after the quote. Otherwise (no request ever claimed it, as when only the Worker's own rate limit refused it) the first read past the signed deadline plus `QUOTED_EXPIRY_GRACE_SECS` (60 s) finishes it, about 6 min after the quote. `failed` with `not_executed` is Retry, and so is a 404: the sweep deletes an intent nothing ever claimed 30 minutes after its quote, so a tab that read nothing until then (asleep or frozen) finds it gone, and nothing moved. Only "not sent yet" reads a 404 so: anywhere else after an execute a 404 holds, since that execute may have been claimed. Any other read ends "not sent yet" (`executing` or later: another execute reached it, shown in doubt; an unmarked `failed`: may have moved). Clearing the amount does not leave it; Reset does, and offering it is the host's call: the dropped intent's signed request stays executable until it expires, so a host that can replay it (a relay, a retry queue) and lets the user sign a new order may execute both. Such a host should not offer Reset here (xochi-widget does not). Suggested copy: "Not sent yet. The solver was busy. You can try again once this order expires." Those deadlines are the server's, compared with the host's clock (`now` on each message): a clock running fast gives up early ("not sent yet" while the Worker could still take the resend), one running slow resends into a refusal the Worker answers with its budget finish. The Worker keeps the same budget server-side and, past it, finishes the intent `failed` with `not_executed` and answers a 502: thrown like any execute, it reads "Still confirming" until the poll reads that `failed`, then Retry. If the tab closes during the wait, this tab does not resend the order; the signed request stays executable until it expires.

## Fee reference

```ts
import { assertFeeBreakdownInvariants, feeBreakdownReconcilable } from "@xochi/client";

if (quote.feeBreakdown) {
  assertFeeBreakdownInvariants(
    feeBreakdownReconcilable(quote.feeBreakdown),
    quote.feeDenomination === "origin" ? { input_amount: request.fromAmount } : {},
  );
}
```

`computeFeeBreakdown` predicts the layers; `FEE_SCHEDULE` mirrors the solver's policy. The invariant check reconciles layers, not the rate; capping it is your policy.
