# Changelog

All notable changes to `@xochi/signer` are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), versions follow [SemVer](https://semver.org/).

## [Unreleased]

## [0.8.0] - 2026-11-08

### Added

- **Passkey recipient keys** (`passkey-recipient.ts`, xochi-sdk#155, epic xochi#833; spec `@xochi/spec` `PASSKEY-RECIPIENT.md`). PROPOSED until product-owner sign-off. `derivePasskeyRecipientKeys({ first, second }, version?)` derives three things from the two 32-byte WebAuthn PRF outputs of one passkey: the recipient CLI's `AccountSecrets` (`secret`, `salt`); a 32-byte AES-256-GCM `wrapKey`; and a 32-byte `pxeStoreKey`, the key of the browser's persisted encrypted PXE store, which is derived on every unlock and never persisted. The derivation is HKDF-SHA-256 (RFC 5869), salt `xochi.recipient.passkey.v1`, a 64-byte wide reduction mod r for the secret and salt. It refuses (`PasskeyDerivationError`) a version other than 1 (`unsupported_version`), an output that is not a 32-byte `Uint8Array` (`prf_output_invalid`) and a zero reduction (`derived_zero`); no message carries key material. Also exports `PASSKEY_RP_ID` (`"xochi.fi"`), `PASSKEY_RP_NAME`, `PASSKEY_DERIVATION_V1` and `PASSKEY_PRF_INPUTS` (the two `prf.eval` inputs), and the `PasskeyPrfOutputs` and `PasskeyRecipientKeys` types. It reproduces the decided reference vectors and `@xochi/spec`'s `shielded-recipient.json` `passkey` section.
- **Passkey backup mode for `BackupPersistenceAck`** (same issue). The type, typehash, purpose and struct are unchanged. The ack now accepts a second `backupFormatId`, `BACKUP_FORMAT_PASSKEY_V1_ID` (`keccak256("xochi.shielded.backup-format.passkey.v1")`, name `BACKUP_FORMAT_PASSKEY_V1_NAME`), whose `backupCommitment` is `passkeyBackupCommitment({ credentialIdHash, rpId, derivationVersion })`: `keccak256(abi.encode(PASSKEY_BACKUP_COMMITMENT_TAG, credentialIdHash, keccak256(rpId), uint32 version))`. That function refuses (`AckEncodingError`) a malformed or zero hash (`not_bytes32`, `digest_zero`), an RP ID other than `xochi.fi` (new code `rp_id_mismatch`) and a version other than 1 (new code `derivation_version_unsupported`). Also exports the `PasskeyBackupDescriptor` type.
- `@noble/hashes` `1.8.0` is now a direct dependency (it was already installed through `@noble/curves`).
- `parseUint(value, field, { allowLeadingZeros? })` and `UintLike`: the strict uint parser XSP uses (canonical base-10 string, non-negative safe integer or bigint). Escrow and shielded inputs follow the same spelling rule; escrow also admits leading zeros.
- The five shielded `*EncodingError` classes expose the refusal `detail` as a property. Names, codes, fields and messages are unchanged.

### Changed

- **`RecipientAckExpected.BackupPersistenceAck` gains an optional `backupFormatId`.**
  - Absent: `verifyRecipientAck` accepts only `BACKUP_FORMAT_V1_ID` and refuses a passkey-mode acknowledgement with `backup_format_mismatch`. An existing caller therefore never accepts passkey mode.
  - Present: the acknowledgement must name exactly that format (`subject_mismatch`).
  - `hashRecipientAck` accepts either format id and refuses any other with `backup_format_mismatch`, as before.
  - Additive: every sealed-file digest, signature, verdict and committed vector is byte-identical, and no existing export changes behaviour for sealed-file input.
- **BREAKING: every XSP uint goes through `parseUint`**: the uint256 `originChainId`, `originAmount`, `destChainId`, `destAmount`, `nonce`, transfer and record `amount` and domain `chainId`, and the uint64 `deadline`, `depositedAt` and `expiry`. Spellings `BigInt` used to coerce now throw "`<field>` must be a non-negative base-10 integer": `""` and `" "` (read as 0), `"0x10"` (16), `" 7"`, `"+7"` and `"007"` (7), `"-0"` (0), and numbers above `Number.MAX_SAFE_INTEGER`. Negatives throw the same message. A uint256 above 2^256 - 1 throws "`<field>` out of uint256 range". Canonical inputs hash as before; committed XSP vectors are unchanged. Migration: pass decimal strings or bigints (convert an `eth_chainId` hex result with `BigInt(hex)` first).
- `@noble/curves` dependency range is `^1.9.0` (was `^1.2.0`).

## [0.7.0] - 2026-11-03

### Added

- **`TokenRegistrationAck`** (xochi#753, OX-12): the fourth recipient acknowledgement. The recipient PXE registered the corridor's OxideToken at `aztecToken` with an artifact of class `aztecTokenClassId` and ran `store_immutables` with immutables hashing to `tokenImmutablesHash`. An enrollment acknowledgement (reuses the binding's nonce and expiry); `verifyRecipientAck` checks `aztecToken` against the binding (`token_mismatch`) and the class and immutables hash against `expected` (`subject_mismatch`), from the verifier's trusted corridor record. Pinned by `@xochi/spec` `conformance/shielded-recipient.json`.
- **`shielded-oxide.ts`**: `oxideTokenImmutablesHash` / `serializeOxideTokenImmutables` (OxideToken's `immutablesHash`, refusing as `OxideEncodingError`), `OXIDE_TOKEN_CLASS_IDS` (the OXDAI class), `isOxideTokenClass` and `requiredEnrollmentAcks(aztecTokenClassId)`: the exact enrollment acknowledgement set for a corridor, three for an OxideToken corridor, two otherwise.

## [0.6.1] - 2026-11-01

Additive (PATCH, so `@xochi/client`'s `^0.6.0` range takes it): no existing export changes.

### Added

- **`advertisedConversionPairs(caps)`** and the `ConversionPair` type: the served `conversion_pairs[]` (Riddler `Conversion.Config.advertised_pairs/0`) as typed `{from, to, sameChain}` entries in served order. An entry without both symbols is dropped, and `sameChain` is `true` only for the served literal `true`. `SolverCapabilities.conversionPairs` keeps its raw records, so no existing export changes.
- **`verifyClaimUserOp`** (ported from `@xochi-fi/shared` 0.2.1, xochi#472): the fail-closed claim check for a claimant holding the scanned ERC-5564 announcement and the per-payment spending key. Same branch order and refusal text as shared's: absent op or EntryPoint, absent announcement, chain mismatch, then `assertPreparedClaimMatchesRequest` with `requireVerified` and the announced token as `expectedToken` (its message returned as `reason`, as `@xochi/client`'s `checkPreparedClaim` does), then `factory` against the announced factory and `factoryData`'s `createAccount(owner, salt)` against the signing key and the announced salt. Every input is required; success returns `{token, amount}` and the caller's announcement for display. `assertPreparedClaimMatchesRequest` is unchanged.
- **`decodeCreateAccountCall`** and `SIMPLE_ACCOUNT_CREATE_ACCOUNT_SELECTOR`: decodes a claim's `factoryData`, failing closed with `UserOperationError` like `decodeErc20TransferExecute`.
- **Receive-side stealth helpers** (`stealth-receive.ts`), moved byte-for-byte from the Xochi widget and `@xochi/shared`: `deriveStealthKeys`, `computeMetaAddress` / `computeMetaAddressFromKeys`, `encodeMetaAddress`, `computeStealthAddress` (the sender-side reference for raxol's stealth conformance suites), `checkViewTag`, `deriveStealthOwner`, `extractViewTag`, `decodeAnnouncementMetadata`, the `STEALTH_DERIVE_MESSAGE`, `STEALTH_SCHEME_ID`, `ERC5564_ANNOUNCER` and `ERC6538_REGISTRY` constants, and the `StealthKeys`, `StealthMetaAddress`, `StealthSettlement`, `StealthAnnouncement`, `StealthPayment`, `StealthDerivation` and `AnnouncementMetadata` types. Private scalars are accepted as bytes or hex. The raxol forward fixture and reverse vectors are vendored under `test/vectors/` and asserted on every run. Matching an announcement to its counterfactual account and reading balances are on-chain reads and stay with the caller.
- **`deriveStealthKeys` refuses anything but a 65-byte signature** (hex, optional `0x`; xochi#679), throwing `STEALTH_SIGNER_UNSUPPORTED`, as the Xochi app does. `0x` (the Safe Apps answer), empty input, the 64-byte compact form, ERC-6492 / ERC-1271 envelopes and non-hex are all refused. It also refuses a result on the new `COMPROMISED_STEALTH_SPENDING_PUB_KEYS` (same list as `@xochi/shared`), and `isCompromisedStealthSpendingPubKey` checks a cached or registered meta-address against it. Every vector is unchanged.

## [0.6.0] - 2026-10-30

### Added

- **Shielded recipient APIs** (xochi#633, xochi-sdk#42): `shielded-recipient.ts` adds the verify-only descriptor digest, pinned stock `SchnorrAccount` address derivation, recipient message wide reduction and Grumpkin Schnorr verification. `shielded-recipient-acks.ts` exports the approved `BackupPersistenceAck`, `SenderRegistrationAck` and `PaymentReceiptAck` byte contracts plus fail-closed async `verifyRecipientAck`: it verifies the descriptor, derives its signing key, reconstructs the binding domain from trusted inputs, checks the exact binding and recipient, pins each type's subject (`expected`: the backup commitment, the registered sender set, or the receipt challenge, terms, operation, transaction, block and amount, with the receipt's token held to the binding's and its network to the trusted one), holds the two enrollment acknowledgements to the named binding's exact nonce and expiry, refuses an expired challenge, then awaits durable atomic consumption of `recipientAckReplayKey(primaryType, bindingDigest, nonce)`, so the two enrollment acknowledgements of one binding, which share its nonce, never collide. Every refusal is an `AckEncodingError`, including malformed input and an unknown primary type (`unknown_primary_type`, from `verifyRecipientAck`, `recipientAckReplayKey`, `hashRecipientAck` and `recipientAckDigest`). Backup persistence binds `keccak256` of randomized encrypted backup bytes and the exact `keccak256(UTF8("xochi.shielded.backup-format.v1"))` format id, never plaintext. New exact dependency `@zkpassport/poseidon2` 0.6.2. Checked against `@xochi/spec`'s `shielded-recipient.json`.
- **`shielded-readiness.ts`** (xochi-sdk#42, pxe-bridge#50): `readinessDomain` / `readinessDomainSalt`, strict `parseReadinessRecord`, `hashReadinessRecord`, `readinessDigest`, `recoverReadinessSigner` and fail-closed `verifyReadinessRecord` for the pxe-bridge readiness attestations. The verifier reconstructs the domain from trusted corridor inputs; pins signer and expected subject (the root optionally, for `Membership` and `RootUpdate`; unpinned, `minBlock` must be the latest attested `rootBlock`); requires positive membership/deployment; enforces consumer-selected age, future-skew and nonzero minimum-finalized-block policy under hard misuse ceilings; and refuses unknown runtime primary types and non-object records with its own `ReadinessEncodingError` / `ReadinessRefusal`. Checked against `@xochi/spec`'s `shielded-readiness.json`.

### Changed

- **`buildDepositAttestationMessage` encodes `to_token` and `recipient` case-exactly unless they are entirely `0x` + hex** (axol-io/Riddler#1254, in lockstep with the server). Those are the fields that can hold a Canton party, so a hint that starts `0x` (`0xAlice::1220...`) is encoded verbatim there. Every other field keeps the plain `0x` fold, because the stealth keys are unvalidated on a public route and can carry a non-hex `0x` value. Every served preimage is unchanged, so `DEPOSIT_ATTESTATION_VERSION` stays `xochi-deposit-attestation:v3`; `assertDepositPartiesCaseBindable` stays until the next attestation version bump, since the unchanged version cannot tell a case-binding server from one that folds. `recipientIsDestinationToken` compares under the same rule, so a recipient and destination token that differ only in the case of a non-hex `0x` value (`0xAlice::1220...` vs `0xalice::1220...`, two Canton parties) are no longer reported as the same address; `0x` + hex addresses still compare case-insensitively.
- The shielded value rules moved to an internal `shielded-values.ts` shared by the three shielded modules. `shielded.ts`'s public names, `ShieldedRefusal` (still its 14 codes, pinned by a compile-time test) and `ShieldedEncodingError` are unchanged.
- **Private-key entry points validate the key before parsing or signing**: exactly 64 hex digits (optional `0x`) and a scalar in `1..n-1` for secp256k1. Malformed spending, viewing, stealth, intent, ERC-3009 and Permit2 keys fail with fixed parameter-specific errors that never include the key. Some keys 0.5.1 accepted now throw: `deriveStealthPrivateKey` used a spending key with fewer than 64 hex digits (an unpadded leading zero) or one not below the curve order without complaint.

## [0.5.1] - 2026-10-25

### Added

- **Moved in from the archived `axol-io/riddler-sdk`** (snapshot, no history) as `@xochi/signer` (was `@riddler/signer`). Every vector digest, signature, typehash and domain separator is byte-identical; EIP-712 domain and contract names (`Xochi`, `RiddlerSolver`, `RiddlerFiller`, `RiddlerEscrow`, `SolverBond`) are unchanged. The `riddler` taker CLI moved to Riddler's private `packages/e2e-signer`.
- **Multi-chain stealth and execute-ownership capabilities** (served by Riddler #1336 and #1346): `parseCapabilities` reads `stealth_chains` into `stealthChains` (`null` when absent or not a list; non-canonical chain ids dropped, repeats collapsed), each chain's `stealth_factory_address` into `chains[].stealthFactoryAddress`, and `execute_ownership` into `executeOwnership` (`true` only for the literal `true`). `stealthFactoryFor(caps, chainId)` names the factory for a single EVM chain listed in `stealth_chains`, never falling back to the deprecated top-level field; `narrowStealthChains(caps, pinnedChainIds)` narrows the caller's own stealth set and never widens it. Both are discovery: a client holds the factory against its own pinned allowlist and never adds to that allowlist from it.
- **`shielded.ts`** (xochi#633, xochi#635): hash-only, inert reference for the shielded settlement contract v1 typed encodings (xochi `shielded-execution.md` §7): `hashNetworkIdentity`, `shieldedDomainSalt`, `bindingDomain` / `termsDomain`, `shieldedDomainSeparator`, `hashRecipientBinding`, `recipientBindingDigest`, and the value rules `assertAztecBytes32` (nonzero and below the BN254 modulus; magnitude does not judge EVM/Aztec provenance, which descriptor/address derivation enforces) and `parseShieldedAmount` (canonical decimal, `0 < x <= 2^128 - 1`), refusing with a typed `ShieldedEncodingError` code. Checked against `@xochi/spec`'s independently generated `shielded.json`. Nothing in the signing path calls it.

### Changed

- **Served spec 0.8.0 support** (from axol-io/riddler-sdk#150): `parseCapabilities` knows `cvm`/`canton_party` and keeps a present-but-unknown `vm_type` as unaddressable instead of `evm`; `sameAddressish` folds case only for `0x` + hex, so Canton party ids stay case-exact; `assertDepositQuoteMatchesRequest` refuses a `0x`-but-not-hex recipient/wallet/refund address (`assertDepositPartiesCaseBindable`), compares the displayed recipient case-exactly unless both are hex, and refuses an `escrow` envelope; `assertPullMatchesIntent` refuses any escrow-bearing quote (`assertNoEscrowEnvelope`) and, given `expectedEscrows`, a pull to a pinned escrow.
- Packaging: npm provenance releases from `release.yml` (`signer-v*` tag); tarball ships `CHANGELOG.md` and a README; TS 6; Prettier `format:check` gates CI and `prepublishOnly`; `engines.node` is `>=22`.
- **`SLASH_ATTESTATION_DOMAIN_NAME` / `_VERSION` and `FILL_ACCEPTANCE_DOMAIN_NAME` / `_VERSION` are one pair, `SOLVER_BOND_DOMAIN_NAME` / `SOLVER_BOND_DOMAIN_VERSION`** (`RiddlerSolverBond` / `"2"`): both structs sign under the SolverBond domain. No digest changes.

### Removed

- Source maps (`dist/*.map`) from the tarball.
- `SolverCapabilities.stealthFactoryAddress`, the deprecated top-level `stealth_factory_address` (the factory on the first `stealth_chains` entry, `null` when that list is empty). Use `stealthFactoryFor` for the chain the claim runs on.

### Fixed

- `assertEscrowBinding` and the pull guard read `expectedEscrows` through one resolver (key grammar: `PinnedEscrows`), so `{"0x2105": E}`, `{"08453": E}` and `" 8453"` pin chain 8453 in both guards (the pull guard skipped them; `assertEscrowBinding` refused them as "no pinned escrow", and the pull guard read `"0b10"` as chain 2). Any other key, two keys for one chain with different escrows, a pin that is not a non-zero EVM address, or a missing `fromChainId` while pins are set refuses to sign.
- `deriveFillSalt` rejects an empty key, like `deriveDestBlinding`.
- `DEBUG` is read without assuming a `process` global, so the bundle loads in browsers without a shim.
- `exports` gives each condition its own types (`require` -> `index.d.cts`), fixing TS1479 for CommonJS TypeScript consumers, directly or via `@xochi/client`'s CJS declarations.
