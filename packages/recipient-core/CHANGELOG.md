# Changelog

All notable changes to `@xochi/recipient-core` are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), versions follow [SemVer](https://semver.org/).

## [Unreleased]

### Added

- `DuplicateOperationIdError` identifies a caller-provided operation journal id collision before
  submission and passes unchanged through live spend and exit, so callers can rotate the id without
  mistaking an older terminal record for the new operation.

## [0.1.0] - 2026-11-08

### Added

- The first 0.1.0 publish is manual from the reviewed `recipient-core-v0.1.0` tag after a
  package-local install and every package gate, because npm cannot attach a trusted publisher
  before the package exists. Attach the protected `npm-publish` trusted publisher immediately
  afterward; the automated `recipient-core-v*` lane publishes subsequent releases publicly with
  provenance. Recipient-core remains intentionally outside the root workspace.
- `RecipientCore.send(..., journalId?)` and `CoreExitRequest.journalId?` accept a caller-provided
  UUIDv4 as the exact operation journal id. Invalid and duplicate ids refuse before submission;
  omitted ids remain generated.
- `restoreJournals` now owns idempotence and returns `"restored" | "already_present"`: empty
  journals restore, an interrupted restore recovers only under the same backup commitment, and the
  complete journal/state set from that backup is a write-free no-op.
- `importCliBackup` erases the plaintext byte array returned by `KeystoreCrypto.open` in `finally`,
  including parse and validation failures.

- **0.1.0: the recipient core** (xochi-sdk#156, epic xochi#833), extracted from `tools/recipient` behind platform ports (`src/ports.ts`: `KeyValueStore`, `LockManager`, `KeystoreCrypto`, `ArtifactLoader`, `AttestationVerifier`, `RecipientKeySource`, `Clock`, `HttpFetch`, `Log`; `WalletStorage` in `src/wallet-storage.ts`). No `node:*`, no builtin module and no `process` anywhere in `src/` (`test/platform-neutral.test.ts`, including an esbuild `platform: "browser"` bundle of both entry points); the vendored Oxide subset still reads the global `Buffer` (README "Ports").
  - Journals over the ports, with the CLI's records byte for byte: `OperationJournal`, `ReceiptJournal`, `ExitJournal`, `StateStore`. A record naming a transaction hash is durable before the transaction is broadcast (`recordBroadcastBeforeSend`).
  - The facade `openRecipientCore(deps)`: `sync`, `balance`, `payouts`, `accountState`, `signReceipt` / `submitReceipt` (the CLI's `receipt` split at the POST), `deploy`, `enrollStart` / `enrollSubmit` / `enrollStatus`, `send`, `exit`, `close`; `importCliBackup` and `restoreJournals(core, backup, sealed)`.
  - `BackupMode`: the sealed backup file or the passkey (`backup-mode.ts`, claim contracts section B). `enrollSubmit` refuses the passkey mode unless `deps.keys.kind === "passkey"`, and while `@xochi/signer` is older than 0.8.0.
  - Browser adapters under `src/browser/**` (subpath `./browser`) and the WebCrypto Nitro verifier under `src/attestation/` (subpath `./attestation`).
- Intent ids are `^[a-z0-9_][a-z0-9_-]{0,63}$` (`INTENT_ID_GRAMMAR`; covers the Worker's route grammar); anything else is refused with a message naming the grammar.
- Every `state.json` read-modify-write in the facade runs under the exclusive `…:operations:state` lease (`stateLockName`).
- `openRecipientCore` refuses a profile recorded for another corridor, and refuses with a clear error when `globalThis.Buffer` is missing. The deps and the secret account are ECMAScript `#private`.
- `restoreJournals` refuses a backup of another corridor, a backup with an unresolved spend, exit or refund (reconcile it with the CLI first), and a profile already enrolled under a different binding; it records `backupCommitment` and `backupTokenAckSignature` as the CLI's `restore` does. It validates the next `state.json` before writing anything and holds a `restore.lock` marker plus `restoreLockName(address)` live lease for the whole restore; `OperationJournal` refuses to begin while the marker exists. With no marker, the exact journals and state from that backup return `already_present` without writes, including an empty journal set whose state records that commitment. An empty journal set without matching state restores; any other destination is refused. After a process or browser termination, only the backup whose commitment is in the durable marker may roll back the partial records and retry. Failed cleanup retains the marker and keeps fund movement blocked until that backup recovers or the profile is recreated.
- `RecipientCoreDeps` has no `crypto` member (nothing read it); `importCliBackup` takes its `KeystoreCrypto` explicitly.
- `sealBackup` refuses a passphrase shorter than 12 characters, as the CLI's sealing does.
- `enrollSubmit` keeps the signed request in `enrollment-request.json` before the POST and resends it unchanged for the same challenge (recipient signatures are randomized, so a re-signed request would fail the Worker's exact-resubmission check). The record is zod-validated (an unreadable one is refused, never posted) and holds the challenge id and expiry, the exact request, and the source signature and backup acknowledgement it was built from. It is created atomically (`kv.create`): a concurrent submit sends the kept bytes. A retry with another signature or backup is refused until the kept request's challenge expires, and the message names that time. Only the Worker's outright refusal forgets the request (`EnrollmentApiError.rejectsEnrollment`, the receipt rule's shape: today only `passkey_recipient_mismatch` 409), never a 401/403/408/429/5xx or an uncategorized 4xx. `state.json`'s backup commitment, binding digest and token acknowledgement come from the request actually sent. The record is removed once the binding is recorded. After a reload, `enrollStart` refuses while a kept request's challenge is unexpired, and the new `enrollResume()` resends it (null when none is kept). Once its challenge has expired, the next submit resends the kept request once: the binding it enrolled is answered (the Worker replays a consumed challenge), and only a refusal (`rejectsExpiredEnrollment`: also the Worker's uncategorized 400 or 409) lets the new request replace it.
- `deploy` writes its tx hash, and whether a sponsored claim paid it, to `deploy.json` before the node can receive the transaction (`AztecPort.deployAccount`'s new `beforeSubmit`, run through `NodeSubmission` like spend and exit; the record is zod-validated, an unreadable one refused). A later `deploy` reconciles a recorded one: included and successful answers its hash; included and reverted is forgotten and refused ("sponsored claim consumed; request a new sponsorship" when a claim paid it), never sent again with the same claim; `dropped` answers its hash once the account is deployed, and is sent again only after the node has kept answering `dropped` for 30 s (`droppedAt` in the record; a load-balanced node may not have seen it yet); anything else is refused. The CLI's `setup` passes no hook and writes nothing new.
- The facade's `operations()` (the journal, oldest first), `receipt(intentId)` (the receipt journal's record; apps need not read `receipts/<id>.json`) and `reconcile()`, the CLI's `operations reconcile` for the operation holding the fund-movement lock (null when none does): a spend or exit with a tx hash completes once its receipt is durably included and is answered unchanged before; a completed exit also journals its `exits/<txHash>.json` record. An L1 refund is refused. A `building` receipt run, spend or exit is aborted (lock released) once the holder its record names is gone, and answered unchanged while that holder lives. A hashless spend or exit never reached the node: `recordBroadcastBeforeSend` makes the tx hash durable before `sendTx`. Only the facade aborts a hashless spend or exit; the CLI's `operations reconcile` still refuses one. An aborted exit keeps its prepared withdrawals in its operation record (the exit journal is keyed by tx hash, and the exit was never sent).
- `OperationJournal.begin` records its holder's `pid` in a spend's or exit's request (no hostname: liveness needs the pid alone, and an older record's `host` is ignored), as `beginReceipt` already did; `abortAbandonedRun(id)` aborts a `building` run whose holder is gone.
- An exit's broadcast record (`recordBroadcastBeforeSend`, which now takes the corridor) names each withdrawal's L1 operation id (`finalizationRequestOperationId`), so an exit interrupted after its broadcast keeps it; `reconcile` derives it for a record written without it.
- `reconcile()` leaves a `broadcast` spend or exit to its holder while that holder runs (it completes the operation itself), so a reconcile racing a live send cannot make it fail. A holder completing an operation already `complete` with its tx hash gets the record unchanged, and `ExitJournal.record` accepts the identical record already written (any other is still never overwritten).
- A durably included spend or exit whose execution reverted is never completed and gets no exit record: `reconcile()` answers it unchanged until the receipt is finalized, then fails it (`finalized-failed`, `operation finalized with a reverted receipt`) with its block number and hash, as the CLI's refund reconcile does. `ObservedTxReceipt` carries the block hash.
- A spend's or exit's submission is decided once, atomically: its holder claims it (`OperationJournal.claimSubmission`, run by `recordBroadcastBeforeSend` before the broadcast record) and a successor's abort of an abandoned run creates the same `operations/submission-<id>-<lockNonce>.lock` key first. Whichever creates it wins: an aborted operation is never sent, and a holder past the boundary is never aborted. The facade's `close()` waits for every send, exit, deploy and receipt run in flight before it releases the session's holder lease, so a running operation never looks abandoned.
- `reconcile()` on the session that holds a record reconciles it once none of that session's runs is in flight (its call returned with the journal write failed); `OperationJournal.abortAbandonedRun` takes `ownRunSettled` and the journal answers `namesThisHolder(record)`. `close()` also waits for a `reconcile()` in flight, and every call after `close()` is refused ("this recipient core is closed"), so nothing takes the holder lease again once it is released.
